# Fact Check

対象に書かれた事実の主張が、一次ソースと一致しているかを確かめるスキル。書き手の意見・提案・評価そのものの是非は判定しない。判定するのは、その意見が根拠として挙げている事実が実在するか、言い方が根拠の強さに見合っているかまでである。

## 実行の原則

- 検証は新しいコンテキストのサブエージェントで行う。対象を書いた文脈を持つメインループで確認すると、「書いたつもりのこと」を事実として読んでしまう
- 対象を読むだけで、編集しない。GitHub・Slack・メールへの投稿もしない
- コマンドの実行は次の範囲に限る
    - 読み取り系のコマンド（`gh` の view・api の GET、`git log`・`git show`・`grep` など）
    - ツールの `--help` と `--version`、公式ドキュメントの取得
    - scratchpad に作った検証用のコードやデータの実行
- リポジトリの変更、外部への送信、課金や本番環境に触れる操作、認証情報を読む操作は行わない。それが必要な主張は「確認できない」とし、確認に要る操作を書いてユーザーに委ねる

## Phase 0 対象と一次ソースの確定

1. 対象をファイルに保存し、行番号で参照できるようにする。チャット上の下書きなら scratchpad に書き出す
2. 対象と一次ソースの版を固定する。読み手が見る版と、自分が読む版がずれていないかを最初に確かめる。たとえば、レビュー依頼が feature ブランチの文書を指しているのに main を読んでいないか、Issue に後からコメントが増えていないか
3. 対象を書いた時点より後に一次ソースが更新されていたら、書いた時点の版と最新版の両方で検証する。報告では「書いた時点から誤り」と「その後の更新でずれた」を分ける。後者は対象の誤りではなく、更新への追従が必要という扱いにする。対象がすでに投稿済みなら、投稿された本文（編集後の版）も確かめる
4. 一次ソースを列挙する。対象が引用・参照している文書、Issue と PR、リポジトリ、公式ドキュメントのほか、正式名称の確認先になる製品の公式サイトも含める

## Phase 1 主張の棚卸し

対象全体を一度に読み、検証できる主張だけを抜き出す。主張ごとに、引用・対象内の位置・型・検証計画を書く。型は次の 7 つである。

1. 引用・要約
    - 「A さんは X と言っている」「文書に X とある」。原文の文言、発言者や著者の取り違え、要約で意味が変わっていないかを確かめる
2. 存在・不在
    - 「X は Y に書いてある」「X はどこにも書かれていない」。不在の主張は、本文・表のセル・図・コメントまで探してから判定する
3. 参照
    - リンク、見出しのアンカー、Issue と PR の番号とタイトル、行番号、コミット。実際に開けるか、意図した箇所を指しているかを確かめる
4. 名称
    - 製品名・機能名・サービス名・API 名・コマンド名・オプション名・設定キー・組織名・人名。公式の表記と一致しているか、旧称や略称を使っていないかを確かめる
5. 技術的な挙動
    - 「コマンド X は Y する」「設定 Z にすると W になる」。公式ドキュメント、ソースコード、実行結果の順に強い根拠として扱う。scratchpad で再現できるなら再現する
6. 数値・日付・状態
    - 件数、金額、日付、バージョン、Issue の open と closed、締め切り。再計算するか、API で取り直す
7. 解釈の根拠
    - 「〜と読める」「〜が薄い」。解釈そのものは判定しない。解釈が挙げている根拠が実在するかと、断定の強さが根拠に見合っているかを判定する

意見・提案・依頼は棚卸しから外す。

## Phase 2 検証

主張ごとに一次ソースを当たり、根拠を「引用＋位置」で記録する。位置は `file:line`、URL、実行したコマンドと出力のいずれかで書く。

- 不在の主張は、使った検索語と探した範囲を根拠に書く。読んでいない範囲を「ない」と判定しない
- 名称は、公式ドキュメントか製品の公式サイトで表記を確かめる。記憶で判定しない
- 二次ソース（ブログ、まとめ記事、AI の回答）しか見つからない主張は「確認できない」とする

## Phase 3 反証

「不正確」「言い過ぎ・ずれ」「不在」と判定した主張と、崩れると結論が動く主張には、反対側の立場で一度当たり直す。対象の書き手や指摘を受ける側が「そこに書いてある」「それは誤解だ」と指せる箇所がないかを探す。反証が成立したら判定を改め、成立しなかったら探した範囲を記録する。

## Phase 4 報告

判定は次の 4 つである。

- 正確
    - 一次ソースと一致している
- 不正確
    - 一次ソースと矛盾している
- 言い過ぎ・ずれ
    - 方向は合っているが、断定が根拠より強い、出所を取り違えている、要約で意味が変わっている、一部は書かれているのに「書かれていない」と言っている
- 確認できない
    - 一次ソースに当たれなかった。何が足りなかったかと、確認する方法を添える

報告は次の形で返す。

```markdown
## ファクトチェック結果

**対象:** <対象と版（ブランチ・コミット・取得日時）>
**一次ソース:** <当たったソースの一覧>

### 要修正
1. [不正確 / 言い過ぎ・ずれ] 「<対象の該当箇所の引用>」（<対象内の位置>）
   - 根拠: <一次ソースの引用と位置>
   - 修正案: 「<before>」→「<after>」

### 更新でずれた（書いた時点では正確）
- 「<引用>」: <書いた時点の版での記述> → <最新版での記述>（<更新したコミットや日時>）

### 確認できない
- 「<引用>」: <足りなかったもの> / <確認する方法>

### 反証で見つかった反論材料
- <書き手や指摘を受ける側が持ち出せる箇所。なければ「探した範囲では見つからなかった」と探した範囲>

### 正確
- <件数>件。リンク・引用など、読み手が信頼の拠り所にする主要なものだけ一行ずつ挙げる
```

- 修正案は、事実に合わせるための最小の言い換えにする。主張の方向を変える必要があるときは、修正案の代わりにそう書く
- 要修正がゼロ件なら、そう書いて終える。件数を埋めるために指摘を作らない

## 他のスキルから呼ぶとき

呼び出し側は、自分のレビューや執筆と並行して、このスキルを新しいサブエージェントで実行する。サブエージェントには次を渡す。

- このファイル（`~/.agents/skills/fact-check/SKILL.md`）を読んで従うこと
- 対象のファイルパスか URL と、その版
- 一次ソースの候補（対象が参照している Issue・文書・リポジトリなど）
- 対象の読み手と目的（「Issue に投稿するレビューコメント」「公開する技術記事」など）
- 結果は Phase 4 の形式で返すこと

呼び出し側は、結果の「要修正」を自分の出力に合流させる。判定ルールを呼び出し側で上書きしない。
