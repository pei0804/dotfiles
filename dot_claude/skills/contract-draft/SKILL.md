# contract-draft: 契約交渉の修正案づくり

契約文書の交渉を支援する。対になる contract-check（受領ファイルの検査）と、リポジトリに置く**交渉台帳**を介して連携する。

## 前提: 正本は相手方にある

契約書ファイルの編集権は多くの場合相手方にある。こちらの成果物は編集済みファイルではなく、**相手が持ち帰らずに取り込める提案**である。提案は `references/proposal-packet.md` の型（現状・修正案・理由・調整余地）で作る。この型は往復回数を直接減らす。相手方の法務が意図を推測せずに済み、反映確認も機械的にできるようになるため。

## 前提: 経緯は台帳で持つ

交渉が進むと、FB は複数の場所（社内法務とのスレッド、相手方とのやり取り、過去の版）に散らばる。毎回すべて読み直すのではなく、論点単位の状態を**交渉台帳**1ファイルに集約する。フォーマットと状態遷移は `references/ledger-format.md` を読む。台帳はスキル内ではなく作業リポジトリに置き（置き場はプロジェクトのドキュメント規約に従う）、締結時にそのまま締結記録へ昇格させる。

## 秘匿情報の扱い

このスキルには組織固有の事実（社名、金額、締結用アドレス、決裁フロー）を書かない。それらは作業リポジトリのナレッジ・メモリ・過去の締結記録から引く。修正案を作る前に、同じ相手方や同種契約の過去の記録がリポジトリにないか探すこと。前回の判断（許容した条項、通った建付け）は交渉の初期値になる。

## ワークフロー（5段パイプライン）

交渉は3者以上（自分・社内法務・相手方の担当者・相手方の法務）で**同時並行**に動く。これを扱うため、台帳は論点表（実質の状態）と確認・依頼キュー（通信の状態）の2層で持つ。詳細は `references/ledger-format.md`。

### 1. 論点化する

対象契約の台帳を探す。なければ `references/ledger-format.md` のテンプレートで作成する（初版の受領時が作りどき）。新しい FB（社内法務の指摘・相手方の対案・contract-check の検査結果・自分の気づき）を、修正案を書き始める前にまず台帳の論点として登録する。既存論点なら経緯に追記する。これを飛ばすと「経緯を踏まえた修正」ができなくなる。

初版の受領時と、契約の性質に関わる前提が変わったとき（業務範囲の認識が変わった等）は、条文単位の検査に加えて `references/consequence-walk.md` の帰結ウォークを回す。建付けレベルの論点（契約類型、権利帰属の構造）は条文の欠落としては現れず、「将来の場面で誰が・何を・誰の金でやるか」に答えられない形で現れるため。ここで出た論点は、社内法務へ渡す前にこちらの言葉で格上げしておくと、法務との議論が最初から深いところで始まる。

### 2. 宛先を決めてキューに積む

論点ごとに、誰に何を確認・依頼するかを決めてキューに積む。まだ送らない。

| 確認したいこと | 宛先 |
|---|---|
| 実態・業務範囲・相手の意図 | 相手方の担当者 |
| 建付けの妥当性・こちらがリスクをどこまで許容するか | 社内法務 |
| 条文の文言 | 相手方の法務（担当者経由で条文案を渡す） |

宛先が違う確認は互いを待たず並行で出す。依存があるときだけ「待ち: Q◯」を付ける。典型は、契約類型が実態確認待ちの間は条文提案を出さない（`references/negotiation-principles.md` の「契約類型から入る」）。どこにも送らず飲む判断をした指摘は、キューに積まず論点を conceded にして理由を書く。

### 3. 条文パケットを作る

相手方の法務に向かう項目は `references/proposal-packet.md` の型（現状・修正案・理由・調整余地）で条文パケットにする。条文は相手方の文書の文体に合わせ、そのまま貼れる完全な形で書く。作成前に `references/clause-checklist.md` で契約類型と不足条項を確認し、`references/negotiation-principles.md` の原則を当てる。

### 4. 宛先ごとに flush する

未送のキューを宛先ごとにまとめて1通にする。宛先の社内往復が1回で済む。社内法務向けは飲む点の先出しを冒頭に置く。相手方向けは、実質論点（条文パケット）と事務項目（表記・日付・締結方式）のセクションを分ける。文面はユーザーの普段のトーンに合わせる（トーン用のスキルがあればそれに委ねる）。社内法務と相手方の両方に関わる整理は、同じ文面を双方に見せると認識が揃う。

### 5. 消し込む

送付したらキューを「送付済み」に、条文パケットを送った論点を proposed にし、パケット本文を台帳に残す。ここに残した条文が、次の版を contract-check で検査するときの突合対象になる。回答が来たら要旨を論点詳細へ転記してキューを消し込む。

## 判断に迷ったら

- こちらが譲る判断（conceded）には必ず理由を台帳に書く。後から読む人（自分を含む）が再交渉すべきか判断できるように
- 提案が通らなかった場合のフォールバックは考えておくが、最初から出さない。社内の判断が固いなら一本に絞って打診した方が速い
- 実質論点がゼロになったら、誤字・表記で締結を止めない。締結後に実害のないものは落とす
