# 機械検査の手順

extract_docx.py の出力（本文テキスト・条マップ）を材料に行う検査の詳細。検算・整合チェックは目視ではなくコマンドや短いスクリプトで行う。件数が多く、見落としの代償が大きいため。

## 参照整合

文中の「第◯条」「第◯項」「第◯号」参照をすべて洗い出し、参照先が存在し、意図した条項を指しているかを確認する。

```bash
grep -oE '第[0-9０-９一二三四五六七八九十]+条(第[0-9０-９一二三四五六七八九十]+項)?' rev_new.txt | sort | uniq -c
```

重点箇所。

- **存続条項**: 列挙されている条番号が、条の挿入・削除後も意図した条項を指しているか。交渉で追加した条項（権利帰属・不具合対応等）が漏れていないか。「解約」による終了が存続事由に含まれているか
- **準用・引用**: 「第◯条に定める方法により」「第◯条第◯項に基づき」の参照先の中身が合っているか
- **定義の参照**: 「以下「◯◯」という」で定義された語が、定義前に使われていないか

## 金額の検算

支払表がある場合、必ず計算する。

- 支払表の各行の合計 = 契約書に書かれた総額
- 初月・末月の変則額（日割り・半月稼働）が期間と整合するか
- 社内の承認資料（費用資料・稟議）の金額と一致するか。承認資料の総額と契約総額に差がある場合、差分が説明できるか（別契約に回る分等）
- 消費税の内外、支払期限の起算（締め日と支払日、金融機関休業日の扱い）

## 表記

スクリプトが半角記号・半角数字の条項参照を検出する。加えて次を見る。

- 契約書の本文に敬語・ビジネスレター調が混入していないか（「ご請求」「お支払い」等。見積書からの転記で混ざりやすい）
- 全角・半角、漢数字・算用数字の混在
- 社名・製品名の表記が正式名称か
- 脱字。特に助詞の欠落（「◯◯関して」等）は機械検出しにくいので、定型条項（反社・解除・譲渡禁止）を一度通読する

## 定型条項の誤記

テンプレート由来の契約書は、定型条項の主語・目的語の取り違えが紛れ込みやすい。解除権・通知義務・賠償責任の主体が「甲」「乙」「相手方」「被◯◯人」のどれで書かれているかを確認し、文意と逆になっていないかを見る。誤記を見つけても、発動場面が想定しにくいものは指摘リストの優先度を下げてよい（締結を止めない）。

## 報告フォーマット

指摘は重み付けして報告する。一覧だけ渡されても、読み手はどれから判断すべきか決められないため。区分は4つで、判定の軸は「その修正の要否が、こちらの方針に依存するか」。

- **必須**: どの方針を取っても修正・確定が要るもの。文言のままだと具体的な実害シナリオが立つ、未確定文言（ハイライト等）が残っている、締結の前提（変更履歴のクリーン化等）を欠く、のいずれか
- **前提確認待ち**: 確認の結果で必須に昇格するか消えるもの。何を誰に確認すると確定するかを添える
- **方針次第**: こちらのリスク許容・建付けの選択で要否が変わるもの。社内法務の判断材料になるよう、水準の評価（同種契約で一般的な範囲か）を添える
- **事務**: 締結を止めないもの。実質論点のクローズ後に1回でまとめて依頼する

```markdown
## 検査結果: {ファイル名}

### 反映された論点
- {論点}: 提案どおり / 文言調整あり（意図は維持）

### 対案が来た論点
- {論点}: {どの一語が変わったか}。{こちらの利用場面がカバーされるかの評価}

### 未反映の論点
- {論点}

### 依頼外の変更
- {条}: {内容}。{実質変更か表記か、影響}

### 指摘（重み付け）

#### 必須
- {条}: {内容と実害シナリオ}

#### 前提確認待ち
- {条}: {内容}。{何を誰に確認すると確定するか}

#### 方針次第
- {条}: {内容}。{水準の評価}

#### 事務
- {内容}

### 機械検査
- 変更履歴: 挿入◯件・削除◯件 / コメント◯件
- 参照整合: {結果}
- 金額: {検算結果}
- 表記・誤記: {件数と内訳}

### 判定
{締結可 / 修正依頼が必要（contract-draft へ） / 要判断}
```
