## コード設計

- 最初に思いついた案を一度疑う
- 賢さより可読性と保守性
- ネストするくらいならアーリーリターン
- 読めば分かる名前にする。説明が必要なら分割のサイン
- API にフィルター機能があればサーバーサイドで絞る。全件取得してローカルでフィルターしない
- タスクに必要な範囲を超えて機能追加・リファクタリング・抽象化をしない。仮定の将来要件に備えない
- コードを直接変えられるなら、フィーチャーフラグや後方互換シムでしのがず直接変える
- 起こり得ないケースのエラー処理・フォールバック・バリデーションを書かない。検証はシステム境界（ユーザー入力・外部 API）にだけ置き、内部コードとフレームワークの保証は信頼する

## 開発スタイル

- 不明瞭な指示は聞き返す。推測で埋めない
- TDD で進める: 探索 → Red → Green → Refactoring
- 想定外が出たら止まる。押し通さない
- 独立したサブタスクはサブエージェントに委任し、完了を待たずに並行して進める。脱線や文脈不足には介入する
- 出す前に staff engineer の目で読み直す。大きめの成果物は新しいコンテキストの検証サブエージェントで仕様と突き合わせる
- 進捗・完了の報告は、このセッションのツール結果で裏付けられることだけ書く。未検証のことは未検証と明示する

## Writing

- 箇条書きは最低限。並列なら箇条書き、順序なら数字付き、それ以外は文章
- その時点で初めて出てくる語には前置きを付ける。固有名詞・製品名・社内呼称・その文書でしか通じない記号（本稼働①など）は、初出の位置で何を指すかを一言添える
- 判断の対象は文脈を置いてから出す。社名・製品名・手段をいきなり出さず、それが何でなぜ候補なのかを先に書く。「なぜ X か」の節が後ろにあっても、X の初出時点で読み手が「X とは？」で止まらないようにする
- 書き終えたら初出の語を洗い出し、前提知識のない読み手が詰まらずに読めるか確認する
- AI向けドキュメント（AGENTS.md など）は断定する。どちらとも取れる書き方を避ける
- 日本語でダッシュ・横線記号（`—` `──` `―`）を使わない。ファイル編集でもチャット応答でも同じ。英語では可
- 日本語で箇条書きの直前に `：` を置かない

## 文書の設計（設計文書・提案・調査記録）

設計文書 1 本で 200 コミット超の書き直しが起きた経験から。往復の原因は文体ではなく、ゴールとスコープの未固定、調査結果の本文への蓄積、根拠のない要素の混入だった。

- 書き始める前に、読み手・読み終えたときに判断できるようになること・扱わないことを 2〜3 行で書き、ユーザーと合わせる。以後の追記はこれに照らして要否を判断し、外れるものは別文書・別 Issue への切り出しを提案する
- 本文を書く前に見出しの骨子（各見出し 1 行の要旨）を出して合意を取る。構成を変えるときも骨子から変える。本文は結論（こうする）から始め、理由と根拠を後ろに置く
- 調査で分かったことを本文に積まない。調査記録は別ファイルに置き、本文はその主張に必要な事実だけを引く。節を足すときは「この節が無いと読み手は何を判断できなくなるか」に答えられるものだけ足す
- 事実・数字・提案するデータ要素（列・キー・概念）は、出典（実測クエリ・実物のシート・ヒアリング・文書）を本文で示せるものだけ書く。定石や一般論から自分で補った要素は、仮説と明記して末尾に置くか、書かない
- 造語と比喩で概念を呼ばない（「継ぎ目」「翻訳」「散る」のような自作の言い換え）。業務で使われている語を使い、1 つの概念には 1 つの名前を通す。名前を変えるときは全文で置換する
- 文書内で完結させる。会議・Issue・ADR の番号だけの参照を置かず、何が決まったかを本文に書く。リンクはリンクテキストで何を指すか分かるようにする
- 決めないことは本文中のぼかし表現ではなく、スコープ節に「扱わない・どこで詰めるか」として明示する。仮説と将来展望は末尾の 1 節にまとめる
- 図は置く段落の主張だけを描く。詳細図（ER 図など）は概念を本文で導入した後に置く。出力後に自分でレンダリングし、矢印の潰れ・はみ出し・色の見分けを確認してから見せる
- 外部ツール（NotebookLM 等）の回答を取り込むときは、文書の問いに答える部分だけを抽出する。そのまま貼らない
- 大きな編集の後は通し読みで整合性を確認する。個数（2 つ／3 つ）、削除した節への参照、用語、文体（ですます）の不一致を直してから提出する

## 言語

- 略語・短縮形を使わない（例: Salesforce ×SF、Snowflake ×SF、Google Workspace ×GWS）
  - コード中の定着略語（API, URL, ID 等）と社内で定着した固有略語（ZERO, CMF 等）は除く
- 日本語の文章にカジュアルな英語表現を混ぜない（例: nit、LGTM、FYI、net positive）。技術用語・製品名は除く
- 公開リポジトリではドキュメントやコミットメッセージを英語で記述する

## Worktree First

ファイル編集を伴う作業を開始する前に、現在の作業環境を確認する。

- mainブランチの場合: worktreeを作成してから作業を開始する
- 既存ブランチでworktree外の場合: worktreeへの移行を提案する
- 作業開始時に「worktreeを作成しますか？」と確認する
- worktree の新ブランチから push するときは必ず明示 refspec を使う: `git push origin HEAD:refs/heads/<branch>`。グローバルに push.default=tracking が設定されているため、`git push -u origin <branch>` でも upstream（origin/main を指していることがある）へ push されるトラップがある。push 後に `git branch --set-upstream-to=origin/<branch>` で upstream を張り直す
</important>
